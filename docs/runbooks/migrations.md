# Migrations

How to change the schema without losing data that already exists.

Related: [`backup.md`](backup.md) (dump and restore), [`schema.md`](../architecture/schema.md) (what the tables are), [#89](https://github.com/BOYSABIO/muttmetrics/issues/89).

## 0. The one thing to know

`alembic revision --autogenerate` loads `Base.metadata` (what the models say the schema should be), inspects the live database (what it actually is), diffs those two **states**, and emits the minimum DDL to turn the second into the first.

It compares two snapshots. It has no idea what you were *doing*. Three consequences:

- **No memory.** Alembic never sees your previous model file. "Metadata has `actual_duration_min`, the database has `actual_minutes`" is indistinguishable from "one column was deleted and another added" — so that is what it writes.
- **Schema only, never rows.** It reads `information_schema`, not your data. It cannot know a column is full of nulls, and it will never write you a backfill.
- **"Minimal DDL to match" is a goal about shape.** Dropping a column is a perfectly good — and cheap — way to make two shapes agree.

**Autogenerate knows what changed, not what you meant.** Everything below is that sentence, expanded.

### What CI does and does not prove

CI spins up an empty `postgres:16` and runs `alembic upgrade head` against it.

| CI proves | CI cannot prove |
|---|---|
| The migration chain applies cleanly from zero | That existing rows survive the upgrade |
| `down_revision` links are intact | That a `drop_column` was intentional |
| The final schema matches the models | That a type change did not round every price |
| Seeds and tests pass against that schema | Anything at all about data — the database is empty |

A destructive operation destroys nothing in an empty database. **Green CI on a migration means the destination is right, not that the journey was safe.**

The thing that would prove the second column is a migration harness that seeds rows, upgrades, and asserts they survived. Deliberately out of scope while this is a single-contributor repo ([#83](https://github.com/BOYSABIO/muttmetrics/issues/83)). Until then the guards are §1, §4 and your own reading.

## 1. Before upgrading a database that holds real rows

```bash
python ops/backup.py        # dump first - see runbooks/backup.md
alembic upgrade head
```

That is the whole habit. The dump is the only thing standing between a misread draft and permanently lost grooms, and it costs seconds. Do it even when the migration "obviously" only adds a column.

If the upgrade goes wrong, [`backup.md`](backup.md) §5 has the restore.

## 2. Reading an autogenerated draft

Autogenerate output is a **draft**. Read every line before it runs. Sort what you see by one question — *does it tell you when it goes wrong?* — because the migrations that cause the worst damage are the ones that cause no visible problem at all.

| Draft | On a table with real rows | Tells you? |
|---|---|---|
| `add_column(nullable=True)` | Nothing to lose | n/a — safe |
| `alter_column(nullable=False)` | Transaction aborts | **Yes, loudly** |
| `drop_column` + `add_column` | Succeeds, data gone | **No** |
| `alter_column(type_=...)` | Succeeds, values changed | **No** |

### 2a. Renames — silent

The model's `actual_minutes` becomes `actual_duration_min`. Autogenerate:

```python
# WRONG - this is a rename, and this is not how you rename
op.add_column("visit", sa.Column("actual_duration_min", sa.Integer(), nullable=True))
op.drop_column("visit", "actual_minutes")
```

No error. Every recorded duration is gone and the new column is empty. What you wanted:

```python
op.alter_column("visit", "actual_minutes", new_column_name="actual_duration_min")
```

Fix `downgrade()` too, or your rollback is itself a data-destroying migration.

### 2b. `NOT NULL` on a populated table — loud

```python
op.alter_column("visit", "booking_channel", nullable=False)
```

Empty database: fine. Real database: `ERROR: column "booking_channel" of relation "visit" contains null values`, and the transaction rolls back having changed nothing. **This is the good case.** The fix is §5.

### 2c. Type changes — silent

```python
op.alter_column("visit", "final_price", type_=sa.Integer())  # from Numeric
```

Postgres demands a `USING` clause only when no cast exists between the types. `numeric → integer` *is* a registered cast, so this runs, and it **rounds every value to the nearest whole number**. 47.50 becomes 48. No error.

When the cast is lossy but you mean it, be explicit so the next reader can see you did:

```python
op.alter_column(
    "visit",
    "final_price",
    type_=sa.Integer(),
    postgresql_using="round(final_price)::integer",
)
```

### 2d. Data is never generated for you — and `default` is a trap

```python
mapped_column(String, default="unknown")  # Python-side, at INSERT time
mapped_column(String, server_default="unknown")  # real DDL DEFAULT
```

`default=` is applied by SQLAlchemy in Python when it inserts a row. It never appears in the schema, does nothing to rows that already exist, and does nothing for anything inserting via `psql`.

`server_default=` becomes an actual `DEFAULT` in the DDL — and adding a column with one **backfills every existing row**.

So `add_column(nullable=False, server_default="unknown")` works on a populated table, while `add_column(nullable=False, default="unknown")` passes CI and fails on yours. If you want the backfill but not a permanent default, drop it afterwards:

```python
op.add_column("visit", sa.Column("channel", sa.String(), nullable=False, server_default="unknown"))
op.alter_column("visit", "channel", server_default=None)
```

## 3. What autogenerate cannot see at all

**CHECK constraints on existing tables.** They are rendered inside `create_table` for a *new* table, which is why `photo`'s constraints made it into its migration — but Alembic does not diff them on tables that already exist. Change a CHECK in a model and autogenerate produces an empty migration while telling you nothing is wrong. Hand-write `op.create_check_constraint` / `op.drop_constraint`.

**Anything missing from `target_metadata`.** This is the dangerous one. If a model is not imported by the time `alembic/env.py` builds the metadata, Alembic sees its table in the database, does not see it in the code, concludes it was removed, and writes `op.drop_table(...)`. CI passes — empty database, nothing to lose — and the upgrade deletes the table on yours.

`env.py` therefore imports the package, not a hand-maintained list of names:

```python
import muttmetrics.models  # noqa: F401
```

`models/__init__.py` imports every model, so the metadata is complete by construction. A list of individual class names works right up until someone adds a table and forgets to extend it.

## 4. The automated guard

`tests/test_migration_safety.py` parses every file in `alembic/versions/`, looks **only inside `upgrade()`**, and fails when it finds a destructive operation that has not been acknowledged.

Scoping to `upgrade()` is the point: every autogenerated `downgrade()` is nothing but drops, so a check that looked at whole files would flag everything and be ignored within a week.

It flags `drop_column`, `drop_table`, `drop_constraint`, `alter_column(type_=...)`, and raw SQL containing `DROP` / `DELETE` / `TRUNCATE`. It deliberately does **not** flag `alter_column(nullable=False)`, which fails loudly on its own, or `UPDATE` in raw SQL, which is how backfills are written.

When the operation really is intentional, dump first and add a line anywhere in the migration file:

```python
# migration-safety: reviewed - dropping legacy array columns, see #98
```

The comment lives in the repo next to the operation it justifies, so a year later the reason is where the code is.

**What it cannot do:** it is structural, not semantic. It cannot tell a safe drop from a catastrophic one. All it does is refuse to let a destructive operation reach `main` without a human having typed a sentence saying they meant it. That is the entire claim — do not read it as approval.

## 5. Expand / migrate / contract

The only safe way to change a shape that already holds data you care about. Three separate migrations, each reversible on its own, with the application still running between any two of them.

```python
# A - expand: add the new shape, nullable, nothing can break
op.add_column("visit", sa.Column("booking_channel", sa.String(), nullable=True))

# B - migrate: fill the rows that already exist
op.execute("UPDATE visit SET booking_channel = 'unknown' WHERE booking_channel IS NULL")

# C - contract: only now is the constraint satisfiable
op.alter_column("visit", "booking_channel", nullable=False)
```

Dropping the old shape belongs in C, long after nothing reads it — [#98](https://github.com/BOYSABIO/muttmetrics/issues/98) did this for `visit.intake_photos` / `after_photos`.

## 6. When `alembic_version` and the real schema disagree

`alembic stamp <revision>` writes a revision id into the `alembic_version` table **without running any DDL**. Use it when the schema is already in the target shape but the version row says otherwise — after restoring a dump taken at a different revision, or after applying DDL by hand.

```bash
alembic current          # what the database claims
alembic history          # what exists
alembic stamp head       # "trust me, the schema is already here"
```

**`stamp` is a claim, not a check.** Alembic does not verify it. Stamp a revision whose migration never actually ran and every later upgrade starts from a false premise — you find out when one of them fails halfway through on a column that was never created. Only stamp when you have *just* confirmed the real schema matches.

## 7. Checklist

1. Edit the models.
2. `alembic revision --autogenerate -m "describe change"`.
3. **Read the draft.** Every `drop_*`, every `type_=`, every `nullable=False` — intentional, or an autogenerate misreading? Check `downgrade()` too.
4. `python ops/backup.py` before touching a database with real rows.
5. `alembic upgrade head`.
6. `pytest` — including the guard in §4.
7. If the migration drops something on purpose, add the acknowledgement line and say why.
